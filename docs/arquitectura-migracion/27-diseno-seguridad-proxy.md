# 27. Diseño de seguridad del proxy de imágenes

Fecha: 15 de noviembre de 2026. Diseño basado en [plan 25](25-plan-correcciones-auditoria.md), [inventario 26](26-auditoria-detallada-image-proxy.md) y el código actual. **No se ha implementado ni desplegado.** La política de hosts aún requiere evidencias de imágenes reales; este documento no declara autorizados dominios inferidos de nombres de proveedores.

## Decisión arquitectónica

Mantener **una función `image-proxy`** y sus contratos `src`, `url` y `cb`, con un **registro de destinos aprobados** en el servidor. Cada entrada debe describir el hostname exacto, esquema, puertos, rutas de imagen admitidas, formatos esperados, si permite redirecciones y qué consumidor lo necesita. El primer host de imagen que puede proponerse con evidencia del código es **`img.youtube.com`** para `/vi/{id}/hqdefault.jpg`; todavía debe comprobarse si redirige y si el formato real coincide. No se autoriza automáticamente `*.youtube.com`, `*.ytimg.com` ni otros nombres por relación comercial.

La función seguirá devolviendo imágenes públicas como binario base64 de Netlify y URL construida por `backendFunctionUrl`. El resolvedor general, biblioteca, miniaturas y exportación seguirán usando la misma interfaz. La comprobación de host es una capa; la dirección IP **efectivamente conectada**, las redirecciones, el contenido y los límites de recursos requieren controles independientes.

**Condición previa al cierre de la política:** el repositorio no revela los hostnames de imágenes guardadas ni de respuestas actuales de IGDB, YouTube Feed/Data API o proveedores de imágenes de usuarios. Una lista cerrada activada hoy rompería rutas reales desconocidas. No se debe desplegar la restricción hasta que esas fuentes estén inventariadas y exista una salida compatible para cada URL que hoy funciona. Esto es un bloqueo verificable del despliegue, no una excepción permanente para aceptar cualquier dominio.

## Revisión del inventario 26 y evidencia pendiente

La búsqueda actual de `image-proxy`, `backendFunctionUrl('image-proxy')`, `proxiedImageUrl` e `imageSearchPreview` confirma los cuatro grupos del informe 26:

- `src/constants/assets.js` emite `src` base64url desde `resolveAssetUrl`/`proxiedImageUrl`; consumidores incluyen noticias, eventos, comunidades, favoritos y `src/services/mediaLinks.js`.
- `src/services/imageLibrary.js` emite `url` desde la previsualización de `EventImageSearchModal`; su biblioteca incorpora campos de posts y resultados IGDB.
- `src/pages/EventSharePage.vue` emite `url` para imagen y logo externos al crear invitaciones.
- `src/pages/PostSharePage.vue` emite `url` y `cb` para imágenes externas de exportación social. `cb` cambia la URL de caché, pero el handler actual lo ignora. `HomeMediaPanel.vue` proxifica miniaturas con el resolvedor general; `mediaLinks.js` construye la miniatura fija `img.youtube.com`.

`GameImagePicker.vue` y `PostEditor.vue` cargan las imágenes devueltas por IGDB **directamente** durante la selección; una URL elegida puede pasar después por el proxy al guardarse y renderizarse en otra vista. El flujo de imagen Nintendo/Xbox de `NowPlayingWidget` y `ProfileGamerPreview` también carga URLs directamente. No hay razón para cambiar esos módulos en esta corrección. El backend de desarrollo `vite.config.js` invoca la misma función y necesita pruebas del mismo contrato.

Información que falta sin consultar producción:

1. Exportar **solo en un entorno local o de prueba autorizado** un manifiesto de hosts, rutas, extensiones y tamaños de URLs ya disponibles allí, sin contenido privado ni tokens de URLs firmadas. Los fixtures actuales usan dominios de ejemplo y el JSON de ejemplo tiene campos de imagen vacíos; no sirven como inventario de producción. Si el usuario proporciona un inventario o muestras anonimizadas de sus URLs existentes, clasificarlas localmente sin hacer peticiones a Firebase real.
2. Guardar respuestas de prueba de IGDB y YouTube Feed/Data API mediante dobles locales o datos de desarrollo ya disponibles; extraer el host final de `cover.url`, `screenshots.url`, `artworks.url` y `thumbnail`. `api.igdb.com`, `api.xbl.io`, `nxapi-presence.fancy.org.uk` y `nxapi-auth.fancy.org.uk` son endpoints de **datos** en este código, no pruebas del CDN de sus imágenes. `store-images.s-microsoft.com` aparece como posible host de portada Xbox en el normalizador, pero esas imágenes no usan hoy este proxy automáticamente.
3. Medir, con servidores de prueba y URLs facilitadas, formato MIME real, firma de archivo, tamaños, redirecciones y destino final de cada host candidato. Registrar únicamente hostname, ruta normalizada, tipo y tamaño; excluir query tokens y datos personales. No se dispone de distribución de tamaños ni de redirecciones de tráfico real.
4. Recorrer localmente los tipos de campo que llegan al proxy: posts (portada, secciones, logos, social), eventos (fondo/logo), banners/iconos de comunidad, imágenes de usuario y miniaturas. Separar URL del mismo origen, `data:` y `blob:` que ya se cargan sin proxy. Confirmar la futura URL HTTPS de backend en el build Tauri; aún no existe una configuración Tauri en el checkout.

## Comparación de políticas

**Lista estricta de dominios global.** Reduce el espacio SSRF, pero una lista construida solo con `img.youtube.com` bloquearía imágenes guardadas y respuestas de terceros no inventariadas. Los comodines de dominio para compensar esa falta amplían demasiado el alcance. No adoptarla sin clasificación por ruta.

**Lista por servicio/consumidor.** Permite entradas exactas de host, ruta y formato para YouTube, imágenes de IGDB verificadas y Storage público verificado. Es la base recomendada. El servidor no debe confiar en un parámetro `service` enviado por el navegador para conceder otro host: debe validar host/ruta de la URL y aplicar una política única derivada de la configuración. Si dos servicios comparten host, sus rutas se unen explícitamente.

**Identificadores internos en lugar de URLs.** Es más fuerte para recursos controlados por Galaxia (ID de imagen de post/evento u objeto de Storage): el servidor resuelve el recurso conocido, sin destino libre del usuario. No cubre por sí solo URL externas ya guardadas, resultados IGDB o miniaturas. Incorporarlo **progresivamente** al subir o normalizar nuevos recursos propios; no convertirlo en condición para el proxy existente hasta migrar los lectores y datos necesarios.

**Eliminar usos innecesarios.** Una imagen cargada directamente por el navegador y no rasterizada podría no necesitar proxy, pero la política CORS y las exportaciones `html-to-image` dependen del origen de la imagen. Quitar el proxy del resolvedor general sin prueba visual rompería potencialmente la web y los PNG. Mantener ahora esos usos; medir por consumidor y retirar solo con pruebas de render y exportación. IGDB/Nintendo/Xbox directos quedan fuera.

**Separar proxies por funcionalidad.** Multiplica handlers, cachés y reglas de seguridad antes de conocer los hosts. Mantener una función con políticas por fuente en datos de configuración. Separar en el futuro solo si una fuente necesita un contrato materialmente distinto, como imágenes privadas autenticadas o transformación de formato.

## Política de destinos y dominios desconocidos

- Registro de **hostnames exactos**, en minúsculas/canonicalizados; sin `*.dominio`, sin sufijos parciales, sin IP literales por defecto. Para cada entrada: HTTPS por defecto, puerto estándar, prefijo de ruta acotado y formatos admitidos. Una entrada HTTP heredada requeriría evidencia de uso y justificación específica; no deducirla del hecho de que el proxy actual acepte HTTP.
- `img.youtube.com` es el único **candidato con URL de imagen explícita del código**. Confirmar su comportamiento con muestra de prueba antes de activar. IGDB, Storage, miniaturas de feed y URLs de usuario reciben entradas solo tras comprobar hostname y rutas reales. Conservar query de recurso cuando sea necesaria, pero no registrar valores sensibles; evitar que una query convierta una ruta permitida en un proxy general.
- Host desconocido: **no hacer fetch desde Netlify** y devolver un error controlado. Para una URL introducida por usuario, ofrecer en la interfaz una carga del archivo al almacenamiento propio autorizado o solicitar revisión del host; la carga desde archivo local evita que el backend tenga que visitar un host arbitrario. Un enlace directo en `<img>` puede servir como vista previa solo cuando la función no exige canvas; no se debe presentar como solución de exportación si CORS la impide. Para URLs heredadas, inventariar y aprobar host/ruta o migrar la imagen a Storage antes del cierre. Ningún host se autoaprueba a partir de una solicitud fallida.
- El endpoint público no puede confiar en `Origin`/CORS como barrera SSRF. Un tercero puede invocarlo fuera del navegador. Tampoco se debe aceptar una allowlist enviada por el frontend. Un host aprobado que redirija a otro host no hereda autorización.

## Protección técnica necesaria

1. **Entrada:** permitir solo GET y exactamente una fuente `src` o `url` más `cb` opcional; validar base64url y longitud antes de decodificar, URL absoluta, esquema, credenciales, fragmento, puerto y ruta. Acotar `cb` a un nonce de longitud/formato razonable o sustituirlo por una versión de imagen controlada para evitar multiplicar entradas de caché. Evitar diferencias entre interpretación de URL del navegador, Node y CDN.
2. **Destino y DNS:** normalizar hostname/IDNA y comparar con la entrada exacta. Resolver registros A y AAAA; negar si la dirección seleccionada o cualquiera que pueda usar el cliente cae en rangos locales, privados, link-local, reservados, multicast o metadatos cloud. Incluir IPv4, IPv6, IPv4 mapeada, NAT64 y representaciones alternativas. Hacer que el cliente HTTP se conecte **a la IP validada**, manteniendo el hostname original para `Host`, SNI y validación TLS. Comprobar/registrar de forma segura la IP realmente usada. Si el runtime no permite garantizar el enlace, no considerar suficiente una resolución DNS previa: usar un transporte que lo garantice o mantener deshabilitado el proxy restringido hasta resolverlo. Esta recomendación coincide con la [guía OWASP sobre SSRF](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html).
3. **Redirecciones:** `redirect: 'manual'`, pocos saltos, y en cada salto volver a validar esquema, host/ruta aprobados, DNS e IP de conexión. Bloquear `Location` ausente, relativo que escape de ruta admitida, ciclo, salto a host desconocido o privado. Probar si los proveedores aprobados requieren redirección y añadir **cada host final exacto** que esté justificado, no una excepción de redirección general.
4. **Respuesta:** timeout total y de lectura; comprobar `Content-Length` sin confiar en él; cortar el stream **antes** de superar el límite efectivo. Aceptar MIME concretos corroborados por firma/decodificación; rechazar HTML declarado como imagen. SVG requiere decisión específica basada en inventario, ya que puede contener contenido activo; no incluirlo solo por `image/*`. Añadir `X-Content-Type-Options: nosniff` y respuestas de error sin caché. Los formatos usados por las vistas actuales se conservan una vez verificados.
5. **Tamaño y plataforma:** el código tiene un máximo de 12 MiB **después** de descargar y devuelve base64. La [documentación actual de Netlify](https://docs.netlify.com/build/functions/configuration/) indica 6 MB para la respuesta almacenada en búfer; la codificación base64 también aumenta el volumen transmitido. El límite de 12 MiB no garantiza una respuesta utilizable en producción. Medir el tipo de función y el límite real aplicable al proyecto; fijar un máximo de imagen **por debajo del límite efectivo de respuesta**, o adoptar una entrega compatible con recursos mayores si los datos reales lo exigen. No reducir el límite a ciegas: primero identificar imágenes legítimas que superen el nuevo valor y prever transformación o almacenamiento alternativo.
6. **Abuso:** cuotas y métricas por función/origen aprobado a nivel de infraestructura o almacén compartido, no `Map` por proceso; límite de tiempo, bytes y redirecciones; caché solo para recursos explícitamente públicos. Un usuario no puede hacer infinitas variantes de `cb` o query para saltarse la caché. No registrar URLs completas ni tokens de Storage. La función no debe reenviar cookies ni Authorization del solicitante al host de imagen.

## Cambios mínimos previstos y archivos

Primera unidad de implementación: configuración de destinos exactos y validador/transporte de `netlify/functions/image-proxy.js`, con pruebas del handler y del transporte en el runtime usado por Netlify. Conservar su ruta, `src`, `url`, `cb` compatible, cuerpo base64, encabezados públicos necesarios para `<img>`/canvas y construcción mediante `src/services/backendClient.js`. `vite.config.js` debe seguir invocando la misma función en desarrollo. La configuración de host aprobados puede vivir en un módulo pequeño de servidor, sin permitir que se incluya en el frontend como autoridad.

Segunda unidad, **solo cuando las muestras lo justifiquen**: adaptar `src/constants/assets.js`, `src/services/imageLibrary.js`, `src/services/mediaLinks.js`, `src/components/home/HomeMediaPanel.vue`, `src/pages/EventSharePage.vue` o `src/pages/PostSharePage.vue` para indicar al usuario una URL no admitida o usar una imagen propia importada. Evitar cambios preventivos a IGDB, Nintendo, Xbox, CORS de endpoints protegidos y reglas Firestore. El objetivo es dejar la web igual para destinos confirmados y hacer explícitos los casos aún no inventariados.

## Pruebas de seguridad

- Rechazo de hostname desconocido, sufijo parecido, subdominio no aprobado, credenciales URL, esquema distinto de HTTP(S), puerto inesperado, URL malformada, `src` inválido, `src`+`url`, `cb` enorme o variable y parámetros extra.
- DNS público, privado y mixto; IPv4/IPv6 y mapeos; rebinding entre validación y conexión; verificación de la IP usada por el socket; SNI/certificado del hostname original; redirección del host aprobado a privado, reservado o no aprobado. Sin conexiones a redes internas reales: DNS y transporte simulados.
- MIME falso, SVG, respuesta HTML, `Content-Length` falso/ausente, stream que supera el límite, servidor lento, descarga interrumpida, múltiples redirecciones, alta concurrencia y abuso de variantes de caché.
- Error de host no permitido sin solicitud aguas arriba; errores JSON no cacheables; imagen válida conserva cuerpo base64, tipo y encabezado CORS público actual. Probar también que la función no reenvía encabezados de autenticación de la solicitud.

## Pruebas de regresión y aceptación

Regresión: `src` del resolvedor, `url` de biblioteca/invitación, `url`+`cb` de PostShare; `img.youtube.com`; imágenes IGDB **antes y después de guardarlas**; portadas, logos y fondos de posts/eventos; banners e iconos de comunidad; PNG/ZIP de ambas exportaciones con imágenes remotas; URLs de Storage y de usuario de los hosts que se confirmen; imágenes Xbox/Nintendo y viewer OBS **sin modificar sus rutas directas**. Ejecutar suites existentes, nuevas pruebas del handler, build y pruebas visuales web. Cuando exista Tauri, verificar imagen y exportación en Windows y Android con `VITE_BACKEND_ORIGIN` HTTPS. No usar producción para validar.

**Criterio de aceptación de seguridad:** ninguna solicitud sale hacia host no aprobado o IP no pública, tampoco tras DNS cambiante o redirección; las respuestas excedidas se interrumpen durante la lectura; MIME y caché se aplican según el recurso validado. **Criterio de aceptación funcional:** todas las imágenes de hosts inventariados y las exportaciones existentes cargan igual en los flujos señalados. Para cada URL heredada de host desconocido debe constar una entrada aprobada o una migración/importación que preserve la imagen antes de activar la política. Sin ese inventario, el diseño está listo para implementar por unidades, pero **no está listo para activar la restricción en la web**.

No se modificó código, configuración, Firebase ni producción en esta fase de diseño. No se ejecutaron pruebas.
