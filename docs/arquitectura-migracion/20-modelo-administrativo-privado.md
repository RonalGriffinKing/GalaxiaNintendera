# Modelo administrativo privado — decisión propuesta

Fecha: 15 de noviembre de 2026. Revisión de arquitectura sobre el código actual y los candidatos locales. **No se han cambiado roles, reglas, código funcional ni producción.** La aplicación Windows/Android todavía no existe.

## Decisión recomendada

Conservar Firebase Authentication para una cuenta individual por colaborador y `users/{uid}.role` como **única fuente de autorización** por ahora: `user`, `publisher` o `admin`. `users/{uid}.isBlocked` invalida el acceso privilegiado. Centralizar **todas las concesiones y retiradas de roles en un endpoint de backend con Firebase Admin SDK**, invocado solo desde la futura aplicación privada. El endpoint debe verificar el ID token, leer en Firestore el rol y bloqueo actuales del actor, y aceptar únicamente las transiciones autorizadas. El dueño principal se identifica por UID configurado en el servidor durante un alta inicial de confianza; ese UID nunca se deduce de una lista vacía ni se incrusta como credencial en la app.

Esta opción aprovecha las comprobaciones `admin()` y `publisher()` del candidato (`security/firestore/firestore.candidate.review.rules:7-14`), que leen el documento actual del actor. Permite retirar un publicador cambiando su rol de forma central y hace que las siguientes operaciones Firestore evaluadas por Rules y las siguientes llamadas al backend lean la revocación. La app local conserva solo la sesión normal de Firebase Auth; el Admin SDK y sus credenciales permanecen en el servidor. La app privada **no constituye una frontera de seguridad por sí sola**: el binario y las llamadas se pueden inspeccionar, de modo que Rules y backend deben autorizar cada operación.

## Alternativas evaluadas

- **`users.role` protegido y endpoint para cambios de rol — recomendada ahora.** Ya lo usan router, UI, Rules y `profile-progress`. Una sola fuente evita sincronizar permisos entre Firestore y tokens. Exige retirar el permiso de cliente admin para cambiar `role`, `isBlocked` y `canChat` de cualquier usuario cuando se prepare la nueva política; de lo contrario el endpoint se podría eludir. El backend deberá comprobar el rol vigente en cada llamada administrativa. En Rules, la lectura `get(users/{uid})` tiene coste y límites, pero el candidato actual ya la emplea y la suite del emulador cubre casos principales. [Firebase: condiciones y lecturas de documentos en Rules](https://firebase.google.com/docs/firestore/security/rules-conditions).
- **Firebase Custom Claims como fuente única.** Solo un servidor con Admin SDK puede asignarlas y Rules puede leerlas desde `request.auth.token`; simplifica algunas Rules y evita parte de sus lecturas. Requiere migrar **todas** las comprobaciones de Firestore, Storage, backend y app. Los cambios de claims llegan al cliente cuando se emite un ID token nuevo o se fuerza su renovación; por ello retirar el rol no invalida de inmediato un token emitido anteriormente. `setCustomUserClaims()` sobrescribe las claims existentes, así que cualquier gestor debe preservarlas deliberadamente. Es más trabajo y añade una ventana de revocación que este proyecto no necesita para la fase inicial. [Firebase: Custom Claims y propagación](https://firebase.google.com/docs/auth/admin/custom-claims).
- **Claims para UI y `users.role` para seguridad.** Crea dos fuentes que pueden divergir; la app puede mostrar controles tras una revocación, aunque Rules los deniegue, o viceversa. Evitarlo. Si en el futuro se adoptan claims, hacer una transición coordinada y probar expiración, renovación forzada y revocación antes de retirar la comprobación de Firestore.

`revokeRefreshTokens(uid)` es útil ante compromiso de cuenta o para expulsar sesiones, pero no sustituye la lectura del rol actual en Rules. El endpoint existente `profile-progress` ya llama `verifyIdToken(token, true)` y comprueba rol/bloqueo para acciones admin; mantener esa comprobación y, si se usan sesiones revocadas, aplicar el mismo criterio al nuevo endpoint. [Firebase: revocación de sesiones](https://firebase.google.com/docs/auth/admin/manage-sessions).

## Evidencia en el proyecto y problemas a corregir

- `src/router/index.js:21-30,116-164,237-251` contiene rutas administrativas en la web y decide por `users.role`. `DashboardPage.vue:102-184` mezcla paneles de publicador y administrador. Esta comprobación de navegación solo controla la interfaz; no autoriza escritura.
- `PublicNavbar.vue:200-214,1176-1189` enlaza al gestor y presenta acciones de administración/publicación; `:850-890` puede crear una cuenta con `role` elegido desde la web. `PublicQuickAdminModals.vue`, importado por `PublicNavbar.vue:14,1349`, contiene controles rápidos que deben salir del build público.
- `UserPanel.vue:490-520,553-566` permite guardar `role`, `canChat`, bloqueo y verificación directamente desde el cliente. `:393-417` contiene un intento de autoalta como `admin` si no hay usuarios; **eliminar ese bootstrap del futuro flujo administrativo**. Una colección vacía, una consulta denegada o un error de red nunca deben otorgar privilegios.
- El candidato actual permite `allow update: if admin()` en `users/{uid}` (`firestore.candidate.review.rules:53`), por lo que un admin de cliente puede cambiar cualquier campo o rol, y permite `allow create: if admin()` (`:39`). Antes de centralizar roles, sustituir ese permiso amplio por una allowlist de campos administrativos no relacionados con autoridad y reservar cambios de rol/bloqueo/permisos al endpoint. Las Rules coincidentes se combinan por OR: otro `allow` amplio anularía la intención. **El candidato local no está desplegado.**
- `netlify/functions/profile-progress.js:8-32` verifica token Firebase con revocación y ejecuta Admin SDK; `lib/progress-service.js:15-36,70-85` relee rol/bloqueo para operaciones de catálogo y dueño. Ese patrón es reutilizable, pero el Admin SDK omite Firestore Rules: el propio backend debe imponer todos los permisos. No usar el endpoint de progreso para otorgar roles mediante un campo nuevo sin una revisión específica.

## Contrato de acceso propuesto

- **Usuario:** web pública, perfil, favoritos, comunidad, eventos, lectura de noticias y funciones normales. No tiene ruta ni módulo de administración en el build web. Conserva los permisos propios previstos por Rules.
- **Publicador:** cuenta Auth propia; entra en la app privada y solo puede crear/editar contenido en los módulos expresamente habilitados. No puede otorgarse `publisher`, convertirse en `admin`, levantar bloqueos, cambiar `canChat`, modificar recompensas, gestionar usuarios ni invocar acciones admin de backend. Sus escrituras deben seguir limitadas por autoría, estado y colección; `publisher()` actual no equivale a administración completa.
- **Administrador:** entra con su propia cuenta en la app privada y usa funciones administrativas. Para autorizar o retirar publicadores, la app llama al endpoint. El principal puede quedar como único actor autorizado a crear o retirar otros administradores, según UID configurado en servidor; no crear administradores adicionales mediante registro público. Todas las operaciones se registran con actor UID, objetivo UID, cambio y fecha, sin copiar contraseñas ni tokens al registro.

Flujo de concesión: el colaborador crea su cuenta normal o inicia sesión; el principal identifica su UID, lo revisa en la app y solicita al endpoint el cambio `user → publisher`. El servidor verifica ID token y principal actual, comprueba que el objetivo existe y no está bloqueado, actualiza `users.role` y deja evidencia de auditoría. El colaborador vuelve a consultar su acceso al abrir o reanudar la app. Para revocar, el endpoint realiza `publisher → user`; Rules y backend leen el nuevo rol en cada operación. No borrar la cuenta ni sus publicaciones. Si se sospecha robo de sesión, revocar también refresh tokens; el backend debe comprobar tokens revocados. Evitar cambios parciales: actualización de rol y registro de auditoría en una transacción de Firestore cuando sea posible. Probar llamadas repetidas y dos cambios simultáneos.

## Separación de aplicaciones sin pérdida de funciones

Construir dos entradas Vue/Vite que compartan componentes, modelos y servicios: build web público sin rutas ni imports de `DashboardPage`, `UserPanel`, `PostEditorPage`, `OverlayEditorPage`, `EventsManager`, `PublicQuickAdminModals` y gestores de recompensas; build privado dentro del contenedor local Windows/Android con esas herramientas y un guard de sesión/rol. Quitar enlaces y formularios de rol de `PublicNavbar`. Esto reduce la superficie descargable en la web; mantener Rules y backend como controles reales. Conservar en la web login/registro ordinario, noticias, perfiles, búsqueda, favoritos, comunidades, eventos, chats autorizados y visor OBS (`/overlay/:id`). Los componentes mixtos (`CommunityPanel`, eventos, perfil y chat) necesitan separar sus controles de gestión de las vistas y acciones de usuario, sin trasladar el módulo público entero. Los enlaces administrativos antiguos deberán redirigir de forma comprensible a la app privada; las URL de OBS deben seguir funcionando.

El orden importa: primero asegurar la autoridad de roles y probar cada permiso; después crear la entrada privada y probar Auth/Firestore/Netlify en Windows y Honor MagicPad 4; por último retirar del build público los módulos administrativos cuando la paridad de funciones esté demostrada. La app privada se distribuye fuera de la web, pero sigue usando Firebase compartido y llamadas HTTPS autenticadas. No guardar una cuenta de servicio, llave privada ni contraseña administrativa en el paquete, archivos de configuración o almacenamiento local.

## Efecto sobre `publicProfiles` y `profile-progress`

`publicProfiles` es una proyección de datos visibles; **no es fuente de roles ni permisos**. No copiar `role`, `isBlocked`, `canChat`, email ni el UID del principal como indicador de autoridad. Nombre, icono, biografía y estadísticas pueden seguir públicos con escritura separada según origen. Un cambio de publicador no exige actualizar el perfil público salvo que se decida mostrar una insignia editorial derivada; aun entonces esa insignia no autoriza acciones. La dependencia de sincronización descrita en `19-perfiles-publicos.md` permanece y no se resuelve abriendo escritura cliente a estrellas/recompensas.

`profile-progress` debe continuar verificando el token y leyendo `users.role`/`isBlocked` en acciones admin. Si se extrae un helper compartido de autenticación para el nuevo endpoint de roles, preservar sus validaciones actuales y distinguir operaciones de progreso del principal. El servicio de progreso puede proyectar estrellas e iconos por Admin SDK en una fase independiente; nunca aceptar valores de recompensa del cliente como autoridad. Las operaciones públicas de perfiles, favoritos y chat no deben depender del rol editorial.

## Decisiones pendientes para el propietario

- Confirmar el UID de la cuenta principal **por un canal seguro de configuración del servidor**, no en el repositorio, cuando se prepare el endpoint. Decidir si otros administradores podrán conceder publicadores; la propuesta reserva esta acción al principal.
- Definir qué módulos editoriales corresponden a `publisher` (posts, páginas, eventos, comunidades, OBS) y cuáles serán exclusivos de `admin`; el dashboard actual no ofrece todavía una política por acción completa.

## Fase 11 — Implementación local del servicio de roles

Implementación candidata, sin despliegue:

- `netlify/functions/role-management.js` verifica `Authorization: Bearer` con Firebase Admin `verifyIdToken(token, true)`, rechaza métodos/body no permitidos y no acepta el UID del actor desde el cuerpo. El endpoint queda desactivado salvo `ROLE_MANAGEMENT_ENABLED=true` y `PRIMARY_ADMIN_UID` configurado en el entorno seguro de Netlify. No hay UID ni credenciales permanentes en el cliente.
- `netlify/functions/lib/role-management.js` comprueba dentro de una transacción el UID principal, su `users/{uid}.role == 'admin'` vigente y que no esté bloqueado. Solo acepta `grant-publisher` y `revoke-publisher`, con `targetUid` como único otro campo. No concede admin ni modifica `canChat`, email, bloqueo u otros permisos. Una cuenta bloqueada no puede recibir publisher; un publisher bloqueado sí puede ser revocado. Los cambios escriben `role`, `updatedAt` y un registro de auditoría sin secretos.
- `firestore.candidate.review.rules` ya no permite creación de perfiles por admin cliente ni edición general de `users`: el administrador de SDK cliente solo puede editar `name`, `description`, `imageUrl`, `updatedAt`; los usuarios conservan su allowlist personal. Roles y recompensas siguen denegados al cliente, incluido admin. El endpoint Admin SDK puede ejecutar la operación acotada porque Rules no autorizan el Admin SDK; la validación debe permanecer en servicio.
- Se retiró de `PublicNavbar.vue` el alta rápida de usuarios con selector de rol y de `PublicQuickAdminModals.vue` el formulario correspondiente. El componente compartido de creación de comunidad se conserva. `UserPanel.vue` ya no presenta selector de rol, no envía campos de autoridad y se eliminó el bootstrap de primer usuario como admin. El componente permanece disponible para reutilización privada; el cambio de publisher se hará mediante UI privada futura que invoque el endpoint.
