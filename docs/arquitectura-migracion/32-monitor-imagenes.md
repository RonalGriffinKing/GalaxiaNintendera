# 32. Monitor de imágenes y enlaces externos

Fecha: 15 de noviembre de 2026. Diseño para la futura administración Windows/Android. Referencias: [27](27-diseno-seguridad-proxy.md), [28](28-inventario-hosts-imagenes.md), [29](29-estrategia-migracion-proxy.md) y [30](30-sistema-dual-imagenes.md). Se revisaron los consumidores locales; no se consultaron proveedores, Firebase ni producción. **No hay implementación ni pruebas ejecutadas en esta fase.**

## Alcance y arquitectura

Registrar **solo imágenes externas nuevas** al guardarlas desde el editor o al escogerlas en la biblioteca. Las publicaciones antiguas continúan funcionando sin registro ni migración automática. El monitor observa referencias de `posts` (portada, hero, secciones, social y carrusel), `events` (imagen/fondo/logo) y selecciones de biblioteca que lleguen a guardarse en una publicación o evento. `src/services/imageLibrary.js` construye parte de su catálogo leyendo posts; una imagen temporal de un resultado IGDB, aún sin asociar, no necesita un registro persistente. Vídeos y enlaces que no sean imágenes quedan fuera de esta primera versión.

Un servicio de comprobación con identidad administrativa lee el registro protegido, usa **el mismo validador y transporte seguro** previsto para el nuevo proxy y escribe resultados en Firebase. No se añade una segunda función que haga `fetch` libre. Firestore comparte estado y alertas entre Windows y Android; el transporte descarga solo para verificar, no almacena automáticamente las imágenes originales. Las comprobaciones no deben modificar la URL del post o evento.

La aplicación Windows puede ejecutar un trabajo local al estar abierta, o un servicio local independiente si se implementa y configura expresamente. Si está cerrada y no hay servicio, no habrá comprobaciones. Android ofrece revisión y reintento manual; su ejecución periódica en segundo plano no debe considerarse garantizada. Para cobertura continua habría que evaluar más adelante un ejecutor de servidor con límites y coste conocidos. Un arrendamiento con vencimiento y actualización transaccional en Firestore permite que **solo un ejecutor** reclame cada trabajo; debe tolerar caída, reintento e idempotencia. No usar cambios en el reloj del cliente como autoridad de permisos; el backend valida rol vigente y rechaza registros o comprobaciones fuera de la política de destinos.

## Datos propuestos

Colección administrativa propuesta `imageReferences/{referenceId}`, con reglas de lectura solo para roles administrativos autorizados y escrituras de estado **solo mediante backend verificado**. El identificador representa una ocurrencia, no solo una URL: dos publicaciones pueden compartir imagen y tener decisiones distintas. Campos mínimos:

- `ownerType`: `post` o `event`; `ownerId`; `fieldPath` estable, por ejemplo `image`, `hero.image`, `sections/{sectionId}/image`, `social.slides/{slideId}/image` o `backgroundUrl`. Evitar índices de array como identidad duradera si el editor reordena secciones. `library` es procedencia, no propietario cuando la biblioteca solo muestra resultados de posts.
- `referenceType`: `external-image`, `legacy-url` solo si se incorpora manualmente una referencia antigua en el futuro, o fuente concreta validada. `originalUrl` se conserva según la decisión del sistema dual; si contiene credenciales, secretos o firmas sensibles, **no aceptarla sin un mecanismo protegido y caducidad adecuada**. Añadir `sourceProvider`, `createdAt`, `createdBy`, `updatedAt`.
- `lastCheckedAt`, `nextCheckAt`, `status`, `httpStatus` opcional, `failureKind`, `consecutiveFailures`, `effectiveHost` y `redirectCount`. Guardar el host final solo si cumple política de datos; no almacenar URL final con query sensible. `lastSuccessfulAt`, `lastConfirmedIncidentAt`, `reviewedAt` e `ignoredUntil` facilitan la gestión.
- `baselineSha256` y `lastSha256` de **bytes descargados completos**; `baselinePerceptualHash` y `lastPerceptualHash` solo si hay decodificación segura y formato compatible. Guardar algoritmo, versión, dimensiones y orientación normalizada para no comparar huellas incompatibles. Registrar tamaño y MIME verificado. Un `ETag` o `Last-Modified` es señal auxiliar, nunca sustituto de comprobación visual.
- `alertId`/`incidentKey`, estado de notificación y número de observaciones, más `leaseOwner`, `leaseUntil` y versión de trabajo para evitar alertas duplicadas o resultados tardíos. Índices y volumen de escrituras se calcularán antes de crear la colección.

No colocar URL original ni miniatura en documentos públicos, `publicProfiles` o logs de acceso. Las reglas Firestore deben impedir que un cliente cambie hashes, resultados, alertas o leases. La aplicación administrativa no recibe credenciales permanentes; usa token Firebase individual y backend que comprueba rol actual. La vista puede editar el destino asociado solo mediante la operación autorizada del editor, seguida de un registro nuevo o una nueva línea base aprobada; no debe editar el documento del monitor para simular que cambió la publicación.

## Comprobación y clasificación

Frecuencia inicial **configurable por fuente**, con valor propuesto de 72 horas para referencias activas y revisión manual inmediata. Distribuir trabajos con variación temporal y limitar concurrencia por proveedor para no producir ráfagas. Aumentar intervalo en recursos estables; disminuirlo para imágenes destacadas solo con necesidad demostrada. Pausar trabajos de publicaciones eliminadas o referencias ya sustituidas. No usar polling permanente desde ambas interfaces. Evitar comprobar una misma URL repetida en una ejecución mediante caché de resultado breve, manteniendo incidentes por referencia.

Cada comprobación hace GET controlado; `HEAD` puede diferir del GET real y un `Range` parcial no permite SHA-256 completo. Validar primero destino, DNS/IP y redirecciones. Verificar código, MIME, firma, dimensiones y límites durante streaming. Un `304` solo es válido si existe un resultado anterior utilizable y se envió un validador condicional; no demuestra igualdad visual por sí solo. Comparar URL original con URL efectiva **sin query sensible** para detectar redirección. El monitor solo detecta que el proveedor ha cambiado la URL canónica si existe un resolvedor de origen autorizado que vuelva a consultar el identificador de imagen; una URL antigua que devuelve 404 no revela por sí sola su reemplazo.

- **Disponible:** respuesta válida con imagen decodificable dentro de límites; hashes iguales o sin línea base aún.
- **Modificada:** SHA-256 distinto en dos resultados válidos; registrar como `bytes_changed`. Solo declarar cambio **visual** cuando comparación perceptual/miniatura normalizada lo confirme por encima del umbral calibrado. Recompresión, metadatos o cabeceras pueden cambiar bytes sin afectar píxeles.
- **Eliminada:** 404/410 confirmado en comprobación posterior, con separación temporal. No confundir un único fallo con eliminación.
- **Redirección:** respuesta llega por uno o más saltos permitidos; registrar host final y distinguir redirección estable de cambio de contenido. Redirección no permitida se rechaza como problema de política, sin visitar destino.
- **Acceso bloqueado:** 401/403, desafío, bloqueo por proveedor o política local. No intentar autenticarse, cambiar identidad ni eludir restricciones; avisar de que puede requerir otra imagen o permiso legítimo.
- **Error temporal:** timeout, DNS transitorio, 429 o 5xx; reintento con espera creciente y respeto a `Retry-After` razonable.
- **No concluyente:** MIME inconsistente, formato no compatible con comparación, respuesta parcial, falta de línea base o error de decodificación ambiguo. No alertar como eliminación o cambio visual hasta resolver.

Para 404/410, 401/403 y diferencias de contenido, exigir al menos dos comprobaciones independientes separadas por un intervalo configurable antes de incidencia confirmada. Un error de seguridad de destino se muestra como bloqueo de política y **no** se reintenta por un camino menos restrictivo. Mantener último resultado válido y mostrar hora exacta del último éxito.

## Seguridad de red

El monitor usa solo referencias ya registradas por un flujo administrativo autorizado y destinos incluidos en la política exacta del nuevo sistema. Un botón «Reintentar» pasa un **ID de referencia**, no una URL elegida por el cliente. No convertir URLs históricas no inventariadas en excepciones automáticas. El modo compatible del proxy antiguo no es fuente de autorización para el monitor. La URL guardada se valida nuevamente en cada ejecución: una edición posterior, DNS nuevo o redirección puede cambiar el destino.

Exigir HTTPS, host/ruta/puerto exactos aprobados, sin credenciales URL ni IP literal; resolución A/AAAA sin rangos privados, loopback, link-local, reservados o de metadatos; conexión fijada a IP pública validada y verificación de IP real del socket con SNI/TLS del host original. Cada salto redirigido repite todas las comprobaciones y respeta un máximo bajo. Si el runtime no permite garantizar la IP conectada, no ejecutar la petición. Cortar el stream por bytes y tiempo total/de lectura; limitar conexiones concurrentes y tasa por host. Rechazar HTML u otros bytes disfrazados de imagen, y procesar SVG remoto solo tras decisión específica. No enviar cookies ni Authorization del usuario al proveedor. Mantener registros sin URL completa, query, tokens, cuerpos o IP del visitante. No usar `Origin`/CORS como protección SSRF.

La descarga del monitor puede generar peticiones adicionales a terceros. Respetar límites y términos del proveedor, no buscar recursos privados ni usar cabeceras para superar bloqueos. Suspender comprobaciones cuando un proveedor prohíba o limite ese uso. El panel no debe ofrecer un «diagnóstico de cualquier URL» que eluda el registro aprobado.

## Miniatura de referencia y consumo

**Opción inicial recomendada:** guardar SHA-256 y, si la decodificación es viable, huella perceptual y dimensiones. No hace falta almacenar una imagen para detectar cambios de bytes o grandes variaciones visuales. Una miniatura de referencia permite al administrador comparar antes/después, pero su copia compartida entre Windows y Android requiere almacenamiento persistente. Sin contratar Storage, se puede guardar una miniatura muy pequeña y comprimida en un documento administrativo de Firestore, **solo si** se verifica el límite de tamaño documental, las reglas y el coste del volumen. Su uso debe ser optativo y separado de la URL original. La miniatura local en Windows ahorra escrituras, pero Android no la verá y se perderá al cambiar de equipo.

Ejemplo de capacidad, **no precio**: con 10.000 referencias y una miniatura de 8 KiB por referencia, los bytes de imagen suman unos 78 MiB; al codificarla en base64 crecen a unos 104 MiB, antes de índices/metadatos. Dos miniaturas (base y actual) duplican esa cifra. Una huella de 32 bytes por referencia requiere unos 0,3 MiB antes de metadatos. Con 10.000 referencias cada 72 horas se programan aproximadamente **3.333 comprobaciones al día**, más reintentos; un promedio de 300 KiB descargados por imagen supone alrededor de **0,95 GiB diarios** de tráfico entrante, sin contar redirecciones, procesado ni salidas. Si cada resultado genera una escritura, son unas 3.333 escrituras diarias; los lectores y alertas añaden operaciones. Para publicaciones reales, medir N, tamaño, cambio y frecuencia antes de elegir plan o presupuesto; no se calculó precio monetario ni se asumió un tramo gratuito. Descargar solo cabeceras reduce tráfico, pero impide detectar cambios de contenido con certeza.

Los hashes perceptuales dependen del algoritmo, tamaño y orientación; elegir y versionar uno tras pruebas con muestras. Un cambio de SHA-256 **no** equivale a cambio visible. Mantener la miniatura anterior hasta que el administrador acepte una nueva línea base; evitar actualizarla automáticamente cuando haya una incidencia. No usar imágenes con derechos o datos privados como miniaturas compartidas sin revisar su almacenamiento y acceso.

## Panel «Estado de imágenes» y notificaciones

En la aplicación privada, listar miniatura si existe, publicación/evento enlazado, campo, host y URL original mostrada con parámetros sensibles ocultos, estado, última comprobación, último éxito, código HTTP y diferencias de hash/miniaturas. Filtrar por estado, antigüedad y fuente. Detalles: historial breve de comprobaciones, redirección, diagnóstico legible y decisión del administrador.

Acciones: **Sustituir imagen** o **Cambiar URL** abre el editor correspondiente y crea nueva línea base solo tras guardar; **Ignorar incidencia** exige motivo y plazo de silencio, sin borrar el diagnóstico; **Reintentar** encola comprobación del ID sujeto a cuota; **Marcar como revisada** reconoce el incidente, no falsifica el estado técnico. Verificar rol vigente en backend para cada acción. Un publicador puede ver o gestionar solo los contenidos autorizados según la política administrativa definitiva; el alcance aún no está implementado.

Crear una notificación interna al pasar por primera vez a incidente confirmado; `incidentKey` estable por referencia, causa y versión de línea base evita repeticiones entre Windows/Android. Actualizar la misma incidencia si persiste; abrir otra tras recuperación y nueva caída. No enviar correo/push por defecto. La interfaz lee cambios de Firestore al abrir y usa tiempo real solo para trabajos/alertas activos cuando aporte valor.

## Pruebas exigidas antes de implementar

1. Registro de una referencia nueva y reemplazo posterior sin alterar documentos antiguos; asociación correcta para campos de post/evento, biblioteca e imagen compartida por dos publicaciones. Denegar al cliente modificación de hashes, estados, roles y leases.
2. Clasificación: 200 válido, 304 condicionado, 301/302 permitidos y bloqueados, 404/410 únicos y repetidos, 401/403, 429, 5xx, timeout, MIME falso, bytes distintos con píxeles iguales, diferencia visual y formato no comparable. Confirmación con observaciones separadas y recuperación sin alertas repetidas.
3. SSRF con DNS/transportes simulados: host no aprobado, URL manipulada, IP privada IPv4/IPv6, DNS mixto o cambiante, IP real distinta, salto a metadatos o host nuevo, tamaño excesivo sin `Content-Length`, stream lento y concurrencia. Verificar que el reintento por ID no acepta URL arbitraria.
4. Dos ejecutores compitiendo, lease caducado, caída antes de escribir, resultado tardío y escritura idempotente. Medir tiempos y bytes en muestras autorizadas; comprobar que logs/Firestore no muestran tokens de URL.
5. Panel Windows/Android: lista, filtros, comparación, reintento, ignorar/revisar, cambio de imagen y sincronización; sin asumir tareas Android en segundo plano. Ejecutar Vitest, pruebas Node, Firebase Emulator y build cuando exista implementación.

## Decisiones pendientes

Faltan hosts y rutas reales de imágenes nuevas aprobables, comportamiento de redirecciones, formatos/tamaños representativos y un transporte que garantice la IP conectada; [28](28-inventario-hosts-imagenes.md) no los confirma. Faltan también elección del ejecutor continuo, disponibilidad aceptable cuando Windows esté apagado, autorización del almacenamiento de miniaturas en Firestore y presupuesto de operaciones. **Hasta resolver destino y transporte, no se deben activar comprobaciones de URLs externas**. El panel puede diseñarse antes, pero no debe habilitar un fetch libre como solución temporal.
