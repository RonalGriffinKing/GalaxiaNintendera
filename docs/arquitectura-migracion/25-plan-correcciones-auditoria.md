## 1. CORS de funciones protegidas y Tauri

### Causa y orígenes comprobados

`backendRequest()` obtiene el ID token con `auth.currentUser.getIdToken()` al usar `authenticated: true` y envía `Authorization: Bearer` junto a `Content-Type: application/json` cuando hay cuerpo. `profile-progress` y `role-management` solo aceptan `POST`; ambos contestan sin cabeceras CORS y devuelven 405 a `OPTIONS`. Desde otro origen, el WebView hará un preflight antes de transmitir esos encabezados, de modo que la llamada protegida no llegará a la autenticación. Desde la web actual, servida en el mismo origen que `/.netlify/functions/`, el flujo puede funcionar sin CORS.

La [configuración oficial de Tauri 2](https://v2.tauri.app/reference/config/#windowconfig) indica que el protocolo local predeterminado en **Windows y Android** usa `http://<scheme>.localhost`, y `useHttpsScheme: true` lo cambia a `https://<scheme>.localhost`; el [cambio de Tauri 2 para Windows](https://v2.tauri.app/start/migrate/from-tauri-1/#new-origin-url-on-windows) identifica `http://tauri.localhost`. Con el esquema predeterminado `tauri`, **`http://tauri.localhost` es el origen esperado en ambos destinos**, no una medición de esta futura app. Si se configura HTTPS, el esperado será `https://tauri.localhost`. Si se registra otro esquema o URL de ventana, habrá que usar su origen efectivo. No incluir `tauri://localhost` por analogía con otras plataformas. En desarrollo, el origen será el que realmente sirva Vite, con puerto exacto. El valor definitivo debe comprobarse con `window.location.origin` y la cabecera `Origin` observada en pruebas de Windows y en la Honor MagicPad 4, antes de cerrar la lista permitida. Cambiar `useHttpsScheme` entre versiones altera el almacenamiento del WebView según Tauri; decidirlo antes de distribuir.

**Endpoints afectados:** `profile-progress` y `role-management` para `POST` autenticado. `igdb` ya gestiona `OPTIONS` para su `POST` público JSON; `xbox-profile` gestiona `OPTIONS` para el GET con `Authorization`. Nintendo y YouTube hacen GET público sin cabeceras personalizadas. `image-proxy` sirve GET público de imagen. Vacaciones e impresora Ruzafa quedan fuera de esta fase. El middleware Vite no registra `role-management`, por lo que una prueba contra Vite no validaría por sí sola ese endpoint.

### Solución recomendada

1. Definir en **servidor** una lista de orígenes exactos para las dos funciones protegidas: dominio HTTPS real de la web pública; origen Tauri efectivo de Windows y Android; y origen de desarrollo con puerto concreto solo en el entorno local. Cargarla desde configuración de despliegue, sin aceptar sufijos, comodines, `Origin: null`, esquemas alternativos ni valores enviados por el cliente. Preparar inicialmente `http://tauri.localhost` como hipótesis documentada; sustituir o confirmar tras crear la configuración Tauri. `VITE_BACKEND_ORIGIN` debe señalar el dominio HTTPS de Netlify en los builds Tauri y ser obligatorio/verificado antes de empaquetar.
2. Responder a `OPTIONS` **antes** de exigir Bearer, pero solo para un origen y petición previstos: `POST`, cabeceras `Authorization` y `Content-Type`, `Access-Control-Allow-Origin` con el origen exacto, `Vary: Origin` y duración de preflight prudente. No usar `Access-Control-Allow-Origin: *` en estas funciones; no habilitar credenciales de cookies porque el cliente usa Bearer. Denegar preflight de origen/método/cabecera desconocidos. Incluir las mismas cabeceras CORS en respuestas `POST` de éxito y error para que el cliente distinga 401/403/409/503 de un fallo de red. Mantener `Cache-Control: no-store`.
3. La respuesta CORS **no autoriza** una operación. Cada `POST` debe seguir verificando ID token (incluida revocación), UID, rol/bloqueo actual y allowlist de acción/campos en backend; la aplicación instalada y `Origin` nunca constituyen credenciales. No enviar claves de Admin SDK ni roles confiables desde Tauri. Decidir expresamente cómo tratar peticiones sin `Origin` de clientes no navegador: nunca otorgarles privilegios por esa ausencia; aplicar siempre token y permisos. El endpoint de roles debe continuar disponible solo cuando su configuración de servidor lo habilite.
4. Mantener `fetch` web como primera opción. El [plugin HTTP de Tauri](https://v2.tauri.app/reference/javascript/http/) evita CORS porque solicita desde Rust, pero añade permiso de red y otra vía de transporte; reservarlo para un bloqueo reproducido en WebView, con alcance de URL estricto, sin usarlo para eludir autorización.

**Archivos previstos:** `netlify/functions/profile-progress.js`, `netlify/functions/role-management.js`, una utilidad CORS compartida pequeña si evita duplicación, pruebas de ambos handlers y configuración futura de Tauri/build. `src/services/backendClient.js` ya admite origen HTTPS y token; solo requeriría una comprobación de configuración del build Tauri, no rediseño. No ampliar CORS de los endpoints públicos sin necesidad.

**Riesgos:** un origen hardcodeado antes de medir el WebView puede bloquear la APK; una lista demasiado abierta permitiría leer respuestas desde otros sitios, aunque no sustituya la autenticación. El origen `tauri.localhost` no identifica de forma fiable una instalación concreta. El preflight puede quedar en caché y ocultar cambios durante pruebas. Los mensajes 401/403 deben conservarse para el cliente. La autenticación Google con popup y la persistencia de Firebase Auth en Android requieren validación aparte; CORS no las resuelve.

**Pruebas necesarias:** tests de handler con `OPTIONS` permitido y denegado (origen, método y cabeceras); `POST` con token válido, ausente, caducado y revocado; usuario, publicador, administrador y cuenta bloqueada; errores con cabeceras CORS; web mismo origen; llamada cross-origin real desde WebView2 y MagicPad 4; `VITE_BACKEND_ORIGIN` ausente o no HTTPS en build Tauri. Comprobar que el preflight no llama a Firebase ni modifica datos y que un `POST` denegado no pasa por la lógica administrativa. Repetir Vitest, Node roles y build.

**Aceptación:** las dos funciones responden correctamente a `OPTIONS` y a `POST` desde los orígenes medidos, rechazan otros orígenes sin permitir privilegios, y mantienen 401/403 y la autorización vigente; la web actual sigue operativa con el mismo contrato. No se considera validado Android hasta probar la APK en la MagicPad.

## 2. Proxy público de imágenes

### Causa y compatibilidad observada

`image-proxy` acepta tanto `src` codificado en base64url como `url` directo y `cb` como parámetro de caché. Solo valida que el destino sea una URL `http:` o `https:`. No limita hostname, puerto, IP ni resolución DNS; hace `fetch` con `redirect: 'follow'`. Esto expone a **SSRF**: un solicitante puede intentar que Netlify consulte una dirección interna, y una redirección puede saltarse una validación inicial futura. El proxy comprueba `Content-Type` mediante el prefijo `image/`, pero confía en el encabezado; acepta también SVG declarado como imagen. Comprueba `Content-Length` cuando existe y el tamaño real **después de `arrayBuffer()`**, por lo que no limita memoria o tiempo durante la lectura. No hay timeout explícito, límite de redirecciones propio ni control de abuso persistente. No se probó que una red interna concreta sea alcanzable en Netlify; el riesgo se desprende del destino libre y del código.

Los consumidores actuales necesitan imágenes de hosts variables: enlaces introducidos por usuarios, imágenes de publicaciones y eventos, Storage, IGDB, miniaturas de YouTube y exportación social. Una allowlist rígida de unos pocos dominios rompería casos legítimos. `src`, `url`, `cb`, la respuesta binaria base64, el tipo de imagen y el CORS de lectura pública son parte del contrato que hay que preservar. Imágenes `data:`, `blob:` y rutas locales que el cliente deja sin pasar por el proxy deben seguir así. Una URL local de OBS tampoco debe enviarse a Netlify.

### Solución recomendada

1. Mantener aceptados los **hosts públicos variables**, pero aplicar una política de destino **públicamente enrutable** antes de conectar: URL absoluta HTTP(S); sin usuario/contraseña, fragmento ni puerto no autorizado; tamaño máximo de URL; rechazo de `localhost`, dominios de red local y literales IP no públicos, incluidos IPv4/IPv6 y representaciones alternativas. Resolver A y AAAA, rechazar cualquier dirección no pública y hacer que **la conexión use precisamente una dirección validada**, para evitar rebinding entre comprobación y conexión. La comprobación solo de texto o un DNS previo sin vincular la conexión es insuficiente. Revisar que el runtime Netlify permita esta garantía; si no, inventariar hosts usados y adoptar una allowlist explícita con un mecanismo controlado para añadir proveedores, antes de restringir el servicio. No usar una allowlist ficticia que rompa URLs guardadas.
2. Usar redirecciones manuales con pocos saltos; volver a validar **cada** destino y su resolución. Establecer timeout, lectura en streaming con corte antes de superar 12 MiB, y rechazar respuesta cuyo tamaño anunciado ya exceda el límite. Aceptar solo formatos de imagen efectivamente necesarios y verificar contenido o firma cuando corresponda; agregar `X-Content-Type-Options: nosniff`. Tratar SVG aparte: inventariar su uso y sanitizarlo de forma demostrable o excluirlo con una alternativa compatible. No basta confiar en `Content-Type: image/*`.
3. Limitar consumo: longitud de parámetros, concurrencia/tiempo, caché de respuestas públicas y métricas de volumen/errores; evaluar protección de tasa del proveedor de hosting sin confiar en un `Map` en memoria de una función efímera. No usar `Origin` como defensa principal de este GET público: las peticiones no navegador lo pueden omitir o falsificar. No añadir autenticación obligatoria, pues `<img>` público y exportación/OBS la perderían.

**Archivos previstos:** `netlify/functions/image-proxy.js` y pruebas nuevas del handler; `src/constants/assets.js`, `src/services/imageLibrary.js`, `src/pages/EventSharePage.vue` y `src/pages/PostSharePage.vue` solo si un caso real exige una adaptación de URL, sin cambiar sus contratos por adelantado. Revisar también `src/services/mediaLinks.js` y `HomeMediaPanel.vue` como consumidores de miniaturas.

**Riesgos:** bloquear imágenes guardadas de un host externo legítimo; DNS rebinding o redirecciones si la validación no cubre la conexión real; respuesta de tamaño falso o sin `Content-Length`; SVG/formatos heredados; caché de una respuesta privada servida como pública. El origen HTTPS de Tauri requiere comprobar que la carga de imágenes y `html-to-image` mantienen CORS y la exportación.

**Pruebas necesarias:** URL pública de cada tipo realmente usado (Storage, IGDB, YouTube, URL de usuario), `src`/`url`/`cb` y misma respuesta binaria; IP privadas y loopback en varias formas; dominio que resuelve a IP privada; cambio de DNS; cadena de redirección pública→privada; puertos no admitidos; respuesta no imagen, MIME falsificado y SVG; cuerpo sin longitud, longitud falsa, más de 12 MiB, respuesta lenta y lectura interrumpida. Probar PNG/ZIP real de eventos y posts y visualización de imágenes en web, WebView y OBS. Las pruebas de seguridad deben usar servidores locales simulados y no consultar destinos internos reales.

**Aceptación:** no se inicia conexión hacia destinos no públicos ni tras redirección; la descarga se corta antes del límite; el endpoint resiste abuso básico sin alterar las imágenes legítimas ni el formato de respuesta; exportaciones y visor conservan las imágenes esperadas. Antes de aplicar una allowlist de host, comparar sus dominios con los datos realmente usados en un entorno autorizado.

La [guía OWASP de SSRF](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html) recomienda validar las direcciones resueltas y desactivar el seguimiento automático de redirecciones; también advierte que comprobar DNS sin fijar la conexión deja una ventana de rebinding.

## 3. Xbox público y candidato Firestore

### Causa y operaciones incompatibles

La ruta `uid` de `netlify/functions/xbox-profile.js` consulta por REST `users/{uid}` para leer `socialLinks.xbox.xuid`; con `diagnostic=images` verifica que el token corresponde a ese UID. La búsqueda por `gamertag` usa un token para buscar una cuenta externa, pero la consulta pública por `uid` puede ser anónima. `src/services/overlayGamerClient.js` también hace `getDoc(users/{ownerId})` para decidir si consulta Xbox/Nintendo. `ProfilePage.vue` lee perfiles y escribe el vínculo Xbox mediante `updateDoc(users/{uid}, {'socialLinks.xbox': ...})`. El candidato Firestore permite `get users/{uid}` solo al dueño o administrador y `get publicProfiles/{uid}` a todos, pero **prohíbe toda escritura de `publicProfiles`**. El código actual no contiene un sincronizador ni lectores reales de esa colección; `publicProfiles` en `ProfilePage.vue` es una variable de vista. La suite del emulador solo prueba un documento público de ejemplo, no la ruta HTTP de Xbox ni la actualización de vínculos.

Así, con el candidato activo, fallarían tanto Xbox de perfiles ajenos como el visor OBS que lee los enlaces desde `users`; el perfil público general tiene más lectores afectados según el [informe 19](19-perfiles-publicos.md). El [REST de Firestore](https://firebase.google.com/docs/firestore/use-rest-api) aplica Rules a solicitudes anónimas o con Firebase ID token; una API key no convierte esa lectura en privilegiada. No usar Admin SDK para leer todo `users` y devolverlo, ni abrir `users` a visitantes.

### Solución recomendada

1. Concretar el esquema mínimo de `publicProfiles/{uid}` para estas integraciones: solo el vínculo Xbox público existente (`xuid`, `gamertag` si se necesita) y las URL/identificadores públicos de Nintendo usados por OBS, dentro de una proyección de perfil de **lista positiva**. No copiar `email`, `role`, bloqueos, `canChat`, credenciales, tokens ni todo `socialLinks`. Conservar en `users` el documento privado y la autoridad de rol. No presentar como disponibles campos aún no comprobados en datos reales.
2. Elegir **un único escritor de confianza** para la proyección, como ya condicionó el informe 19. La opción de menor infraestructura es extender el servicio autenticado existente `profile-progress` para leer `users/{uid}` y escribir una proyección permitida con Admin SDK, derivando UID del token. Para alta, edición/desvinculación, bloqueo/baja y cambios de progreso, definir disparadores explícitos o una acción de sincronización idempotente; no confiar en que el navegador envíe campos públicos privilegiados. Si la actualización de vínculo privado y proyección debe ser inmediata, hacerla en una misma operación/ transacción de backend con validación de la entrada; si se conserva temporalmente la escritura propia actual, añadir reconciliación y no declarar sincronía atómica. Las Rules candidatas pueden seguir denegando escritura cliente de `publicProfiles`.
3. Una vez que haya documentos públicos y sincronización probada, cambiar **ambos** lectores: `xbox-profile` leerá por REST `publicProfiles/{uid}` para la ruta `uid`; `overlayGamerClient` leerá ese documento para Xbox/Nintendo. Mantener búsqueda `gamertag` con autenticación y diagnóstico privado del dueño; el token de esas acciones no necesita autorizar la lectura de la proyección pública. Preservar resultado y errores actuales de `fetchXboxProfile`, caché e integración `NowPlayingWidget`. Sin proyección, devolver un estado controlado y medible; **no** volver a leer `users` por una excepción pública. Un backfill idempotente de perfiles existentes, revisado por privacidad, será necesario antes de cambiar la política; este plan no lo ejecuta.
4. Completar la migración de los demás lectores públicos de perfiles del informe 19 antes de considerar desplegable el candidato Firestore. La corrección de Xbox por sí sola no hace segura ni funcional la web completa bajo esas reglas.

**Archivos previstos:** `netlify/functions/xbox-profile.js`, `src/services/overlayGamerClient.js`, `src/pages/ProfilePage.vue` en el punto de vinculación, `netlify/functions/profile-progress.js` y `netlify/functions/lib/progress-service.js` si se elige el escritor existente, pruebas del endpoint y del emulador. El candidato `security/firestore/firestore.candidate.review.rules` ya define lectura pública y escritura cliente denegada para `publicProfiles`; no ampliar `users` ni añadir reglas globales. La proyección general y los otros lectores se rigen por el informe 19.

**Riesgos:** perfiles heredados sin documento público; vista incompleta o enlace Xbox obsoleto tras desvincular; confundir un XUID público con una prueba de propiedad de la cuenta externa; coste/latencia de sincronización; exponer por accidente campos privados al proyectar un mapa entero; desplegar Rules antes de sustituir todos los lectores públicos. El endpoint Xbox conserva su secreto de proveedor únicamente en servidor.

**Pruebas necesarias:** emulador con visitante, dueño, tercero, publicador y administrador: `users` privado, `publicProfiles` legible y sin escritura cliente, incluso del dueño; proyección sin email/roles/tokens; vincular, sustituir y desvincular Xbox; perfil heredado sin campos; usuario bloqueado y borrado; ruta `uid` pública de Xbox y `diagnostic` limitado al dueño; OBS/`NowPlayingWidget` anónimo con Xbox y Nintendo; regresión de búsqueda `gamertag`; respuestas de OpenXBL simuladas. Ejecutar la suite candidata completa **además** de los casos nuevos, sin ensanchar permisos para que pase. Probar también los demás lectores públicos del informe 19 antes de plantear un despliegue de reglas.

**Aceptación:** visitante y miembro ajeno ven el vínculo Xbox consentido y el overlay funciona sin leer `users` ajeno; el dueño puede vincular/desvincular y la proyección converge de forma demostrable; ningún cliente escribe roles, recompensas ni otro perfil público; no aparece información privada; las funciones existentes conservan su contrato. No se afirma que producción esté protegida mientras no se verifiquen reglas desplegadas por separado.

## Secuencia propuesta y límites de esta fase

1. Preparar pruebas de CORS de los dos handlers y confirmar origen real en un prototipo/configuración Tauri antes de fijar valores de servidor. Implementar la respuesta CORS exacta, sin cambiar autenticación.
2. Inventariar destinos de imagen legítimos y endurecer el proxy con pruebas de SSRF, redirecciones, tipo, tamaño y exportación. Priorizarlo como riesgo de backend existente, independientemente de Tauri.
3. Definir y poblar la proyección `publicProfiles` mediante un escritor confiable; cambiar lectores Xbox/OBS y luego los restantes lectores públicos. Ejecutar pruebas de privacidad y Emulator antes de discutir cualquier despliegue de Rules.
4. Repetir Vitest, pruebas Node de roles, Firebase Emulator aislado y build; después hacer pruebas de navegador/WebView/OBS. Cada corrección debe ser reversible por archivo o función, con su prueba específica. Toda intervención en producción, migración de datos o publicación de reglas pertenece a una aprobación posterior.

**No se ejecutaron pruebas en esta fase de planificación.** No se editaron funciones, Rules, datos ni configuración de despliegue.
