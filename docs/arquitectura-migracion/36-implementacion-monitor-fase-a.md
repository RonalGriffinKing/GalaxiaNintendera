Fecha: 15 de noviembre de 2026. Revisados los informes 33 y 35 y el estado local actual. No se modificó código funcional, reglas ni datos; no se ejecutaron pruebas ni despliegues.

## Resultado

La implementación no puede avanzar de forma segura en este estado sin resolver cómo se autorizan y coordinan las escrituras del documento propietario, `imageReferences`, `imageIncidents` e `imageHistory`. Este informe registra los bloqueos encontrados; no declara completada la Fase A.

## Bloqueos verificados

- `src/components/posts/PostEditor.vue` ya tiene cambios locales sustanciales en el mismo archivo: campos de frase destacada, vista previa y adaptación/cancelación de IGDB. El guardado de posts sigue ejecutando `updateDoc` o `addDoc` desde el cliente. No se alteró ese archivo porque cualquier integración debe componerse sobre su diff actual y cubrir ambos flujos sin perder esos cambios.
- `src/components/modals/EventEditorModal.vue` guarda directamente en `galaxyEvents` con `addDoc`/`updateDoc`; `backgroundUrl` es el campo de imagen y `imageUrl` se lee como legado. No existe transacción conjunta con el registro del monitor.
- El candidato `security/firestore/firestore.candidate.review.rules` no tiene permisos para `imageReferences`, `imageIncidents` ni `imageHistory`; la regla final deniega colecciones desconocidas. Tampoco permite ahora una escritura atómica validada que abarque imágenes y documento propietario. El candidato es local y no prueba el estado de producción.
- La regla candidata de posts permite a administradores crear/actualizar documentos con un margen amplio. Añadir `getAfter()` de forma aislada para el monitor no limita por sí solo los campos del post ni resuelve la autorización de eventos. Se necesita diseñar y probar una allowlist/transición para las escrituras conjuntas, evitando que los permisos coincidentes se sumen mediante OR.
- Las referencias a secciones y diapositivas no tienen en lo inspeccionado una identidad estable garantizada; un índice como `sections/2/image` se vuelve incorrecto al reordenar. El modelo necesita ID estable o reconciliación por revisión de documento antes de activar registros.
- La suite actual valida el candidato existente; añadir permisos en Rules sin pruebas de creación/actualización conjunta, usuario bloqueado, visitante, admin y operaciones sobre campos protegidos no sería una base suficiente para habilitar datos.

## Diseño seguro pendiente de concretar

Antes de tocar los guardados, elegir y probar una de estas dos vías:

1. **Lote cliente con reglas explícitas:** un mismo `writeBatch` escribe post/evento, referencias y entradas de historial; Rules comprueba con `getAfter()` que cada referencia coincide con el campo de imagen resultante y que la asociación pertenece al contenido editable. El cliente jamás escribe disponibilidad técnica, rol, autor de auditoría o lease. Las incidencias tienen transiciones limitadas.
2. **Endpoint autenticado:** reemplaza solo las operaciones de guardado pertinentes por una operación transaccional que valide Firebase ID token, estado bloqueado y rol actual de Firestore; aplica allowlists, verifica propietario/versión y escribe los documentos relacionados en una transacción. Admin SDK omite Rules, por lo que las validaciones deben ser completas en el servicio. Reutilizar `backendClient.js`, no crear cliente HTTP/Firebase duplicado.

No se elige aquí una vía sin pruebas de compatibilidad con el flujo actual y con la suite del candidato. Para ambas, definir IDs estables en sección/slide o la regla de reconciliación, archivo/retirada lógica al eliminar o cambiar imagen, e idempotencia ante reintento.

## Decisiones definitivas de diseño (Fase 1.7.10)

Esta sección resuelve **el diseño** de los dos bloqueos anteriores. La implementación y su validación siguen pendientes. Se inspeccionaron `savePost()` y su diff local, `saveEvent()`, los normalizadores de secciones, social y hero, y las reglas candidatas. No se modificó ninguno de esos archivos.

### 1. Coordinación: guardado existente + reconciliación autenticada

**Publicaciones:** conservar el `updateDoc`/`addDoc` actual y el `writeBatch` que desancla entradas sobrantes de Inicio. Tras un guardado correcto, llamar a **un único servicio Netlify autenticado del monitor** con ID del post, `operationId` estable para ese intento y las claves de imagen nuevas/cambiadas. El servicio verifica ID token, consulta `users/{uid}` para rol vigente y bloqueo, y lee el post **ya persistido**. Autoriza al administrador; para un publisher activo permite solamente sincronizar referencias de un post cuyo `authorId` sea su UID, sin permitirle leer o gestionar incidencias administrativas. Valida que cada clave solicitada exista en el documento y extrae la URL **del documento**, nunca del cuerpo de la petición. Una transacción Admin SDK crea/actualiza referencias e historial con IDs deterministas y solo si cambió la URL/versión. No altera el post. El backend debe validar estrictamente operación, propietario, claves, longitud, protocolo de referencia y campos; Admin SDK elude Rules.

**Eventos:** conservar `updateDoc`/`addDoc` del modal; capturar el ID devuelto por `addDoc` y sincronizar `backgroundUrl` (y cualquier otro campo confirmado en el flujo de guardado) con el mismo servicio después del commit. Para publisher, comprobar `createdBy` del evento; la regla candidata hoy permite a cualquier publisher actualizar eventos, pero el monitor **no** debe heredar ese alcance amplio. El administrador puede sincronizar cualquiera. No asumir que `imageUrl` heredado es una referencia nueva. La transacción del backend aplica el mismo contrato de idempotencia que posts.

**Por qué se elige esta estrategia:** `runTransaction` cliente o `writeBatch` del post/evento junto con referencias exigiría reglas de validación cruzada para campos profundamente anidados y cambios al `writeBatch` existente de home pin. Las reglas candidatas actuales no prueban ese contrato y una regla permisiva para admin no verificaría que una referencia corresponde al campo. Un backend que **sustituya** todo el guardado tendría que reproducir la amplia normalización, validación y lógica de home pin. La reconciliación posterior conserva los guardados y concentra la validación del registro en un punto. Su coste es una ventana en que el contenido está guardado y el monitor aún no refleja el cambio; esta ventana debe hacerse visible y reparable, no ocultarse.

**Reintento seguro:** el editor genera `operationId` antes del guardado y lo conserva hasta conocer el resultado de sincronización. Si el guardado principal falla, no llama al monitor. Si sincronizar falla, muestra «contenido guardado; registro del monitor pendiente» y permite reintentar con el mismo ID. El backend usa transacción: consulta el documento actual, verifica los campos elegidos, y compara la versión/URL contra referencias existentes. La clave de historial incorpora `operationId` y la clave de referencia; repetir la petición no añade entradas. Si otra edición modificó el campo entre guardado y sincronización, se rechaza la petición antigua por **versión de documento** (`updatedAt` más un `mutationId` o revisión monotónica controlada para nuevas escrituras); no se asocia la URL equivocada. Si el editor se cierra o pierde la respuesta, una cola local de operaciones pendientes puede reintentar; para supervivencia entre dispositivos, guardar en el documento nuevo un marcador de sincronización pendiente o una pequeña operación pendiente en Firestore protegida. No recorrer todos los posts ni registrar imágenes históricas al abrir el panel.

**Límite de atomicidad:** ningún backend puede volver atómico un `addDoc` cliente que ya terminó con una transacción posterior. Se garantiza **ausencia de referencias huérfanas y duplicados** verificando el propietario/URL actual y usando IDs/transacciones; la **completitud inmediata** del monitor no queda garantizada ante caída entre pasos. Un indicador pendiente y reintentos son criterio obligatorio de aceptación. Si se exige atomicidad estricta también para completitud, habrá que mover el guardado completo al backend o a un lote cliente con reglas cruzadas y volver a evaluar ese coste. Esta decisión conserva el flujo actual y la eventual consistencia del monitor.

### 2. Identidad persistente sin migración histórica

- **Post/evento:** usar el ID Firestore existente. En creación, conservar el ID devuelto por `addDoc`; no deducirlo del slug o título. El evento existente usa `props.event.id`.
- **Ranuras escalares:** claves fijas (`post:image`, `post:coverImage`, `post:thumbnail`, `post:hero.image`, `post:hero.logoUrl`, `post:social.image`, `event:backgroundUrl`). Una referencia representa **una ocurrencia**, no una URL; la misma URL en dos campos crea dos referencias.
- **Sección:** introducir `mediaSlotId` aleatorio estable en **secciones nuevas**; preservarlo al mover con `splice`. Al duplicar sección, generar otro ID (el `JSON.stringify` actual copia todos los campos, por lo que debe reemplazarse solo ese ID). Al eliminar, archivar referencia de ese ID cuando el cambio quede guardado. `normalizePostSections()` hoy reconstruye cada sección y descarta campos desconocidos: debe conservar/validar `mediaSlotId`. Una sección antigua sin ID sigue renderizando igual; no se le asigna ID por una lectura ni por un guardado sin cambios de imagen. Si el administrador cambia expresamente la imagen de una sección antigua, asignarle ID en esa edición, sin tocar otras secciones históricas.
- **Diapositiva social:** introducir `mediaSlotId` propio para cada slide nuevo y conservarlo en `normalizeSocialContent()`, que hoy lo descartaría. En importación JSON, preservar ID existente solo si pertenece a la misma diapositiva y es único; generar uno nuevo para una copia o slide nuevo. `sectionIndexes` permanece como mecanismo editorial actual y **no** se usa como identidad del monitor. `PostSharePage.vue` genera IDs visuales como `social-${index + 1}`; son temporales de render y no sustituyen `mediaSlotId`.
- **Galería hero:** cada elemento nuevo recibe `mediaSlotId`; `normalizeHomeHero()` debe conservarlo, pues actualmente produce solo `url`, `alt`, `position`. El editor reconstruye la galería desde líneas de URL y reutiliza el objeto existente si coincide la URL; para cambios de URL o duplicados hace falta conservar la ranura por edición o generar una ranura nueva explícita. Los elementos históricos sin ID siguen visibles sin registro automático.
- **Referencia:** ID determinista por `ownerType`, `ownerId` y `fieldKey`/`mediaSlotId` (codificados sin `/` y validados). Conserva `referenceVersion` creciente; cambiar URL incrementa versión y agrega historial, sin crear otra referencia activa para la misma ranura. La identidad del recurso IGDB no sustituye la de la ocurrencia. No calcular la clave desde la URL, índice del array, título ni `Date.now()`.

Para posts existentes: no migrar ni añadir IDs al cargar. Registrar solo imágenes elegidas/añadidas **después** de habilitar el monitor; una URL vieja no pasa a ser «nueva» por reordenar secciones o guardar texto. El servicio recibe claves explícitas de ranuras modificadas y comprueba el campo actual antes de escribir. Las ranuras que ya fueron registradas sí se reconcilian al sustituir/eliminar imagen. En publicaciones nuevas, registrar todas las ranuras de imagen no vacías tras el primer guardado. No hay colección de biblioteca independiente: `src/services/imageLibrary.js` extrae imágenes de posts; una selección de biblioteca se registra en la ranura del post/evento donde se guarda.

### 3. Modelo definitivo de Fase A

`imageReferences/{referenceId}`: `ownerType`, `ownerId`, `fieldKey`, `mediaSlotId` cuando corresponda, `referenceType`, `originalUrl`, `referenceVersion`, `availability: 'unverified'`, `adminState: 'active'|'archived'`, `createdAt`, `createdBy`, `updatedAt`, `lastOperationId`. Los campos de Fase B (`lastCheckedAt`, HTTP, SHA-256, hash perceptual, IP y redirección) **no existen** en A. Si se registra una URL firmada, limitar lectura, mostrarla sin query en panel/log y definir caducidad; nunca copiar secretos a historial. `originalUrl` coincide con el valor guardado en el campo propietario al confirmar sincronización.

`imageIncidents/{incidentId}`: `referenceId`, `referenceVersion`, `reason`, `adminState: 'open'|'reviewed'|'ignored'|'resolved'`, `reportedBy`, `reportedAt`, `reviewedAt`, `ignoredUntil`, `resolvedAt`, `lastOperationId`. Creación manual por administrador y clave de incidencia abierta determinista por referencia/versión/causa; un incidente resuelto puede dar lugar a otro nuevo con nueva secuencia. Las observaciones se agregan como eventos de historial para evitar arrays ilimitados. **Revisado/ignorado/resuelto son estados administrativos**, sin efecto sobre `availability`.

`imageHistory/{entryId}`: entrada inmutable con `referenceId`, `incidentId` opcional, `operationId`, `kind` (`registered`, `url-changed`, `archived`, `incident-opened`, `note-added`, `reviewed`, `ignored`, `resolved`), `actorUid`, `at` y metadatos acotados. ID determinista para cada operación y elemento; no guardar URL anterior firmada en cada evento. Las **notificaciones** se derivan de incidencias abiertas/no silenciadas y cambios recientes, sin cuarta colección ni correos.

### 4. Permisos Firestore de estas tres colecciones

Añadir en el **candidato local**, en una implementación posterior, coincidencias exactas para las tres rutas; no cambiar producción ni añadir regla global. En la primera versión, **SDK cliente: `allow read` solo si `admin()`; `allow create, update, delete: if false`**. El endpoint de monitor, con Admin SDK, es el único escritor y verifica ID token revocable, `users.role` vigente, `isBlocked`, autorización por operación y forma completa de cada documento. Así el cliente no puede cambiar `availability`, roles, propietario, historial o resultados técnicos. Publisher, usuario normal y visitante no leen ni escriben estas colecciones desde cliente. La sincronización de contenido de un publisher ocurre únicamente detrás del endpoint y solo para post propio/evento creado por él; no habilita gestión de incidencias. Si más adelante se autoriza lectura parcial de publisher, requerirá un modelo separado para no exponer URLs/observaciones de otros y pruebas de consultas.

El `deny` final existente no revoca un `allow` específico; comprobar superposiciones porque Rules combina permisos mediante OR. El endpoint nunca acepta `availability`, `actorUid`, `ownerId` arbitrario, `adminState` técnico, ni URL del cliente como autoridad. Para cambios de incidencias, valida transiciones y hora del servidor. Las reglas candidatas de `posts` y `galaxyEvents` siguen controlando sus guardados actuales; no se amplían para el monitor.
