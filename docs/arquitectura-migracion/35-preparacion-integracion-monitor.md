## Modelo de datos propuesto para Fase A

Separar **disponibilidad técnica** de **flujo administrativo**. No presentar como comprobada una imagen solo porque se registró o un usuario la vio. Timestamps preferentemente del servidor para orden y trazabilidad. Establecer límites de longitud y formato antes de escribir; URL con credenciales embebidas se rechaza y una URL firmada requiere decisión específica de privacidad/retención.

1. `imageReferences/{referenceId}` — una **ocurrencia** de imagen nueva. `ownerType: post|event`, `ownerId`, `fieldKey` estable, `referenceType`, `originalUrl`, `source: editor|library|igdb|manual`, `createdBy`, `createdAt`, `updatedAt`, `archivedAt` opcional, `referenceVersion`. `availability: unverified` es inmutable en A. `lastCheckedAt`, códigos HTTP, hashes y datos de red quedan ausentes. El ID no se deriva solo de URL: dos usos del mismo enlace son referencias diferentes. Para arrays de secciones/diapositivas, usar identificadores estables o reconciliar sobre una versión del documento; un índice no identifica permanentemente una imagen reordenada. Una imagen de biblioteca se asocia al post/evento que la utiliza; no crear otra copia por aparecer en el buscador.
2. `imageIncidents/{incidentId}` — incidencia manual vinculada a `referenceId` y versión. `reason`, observaciones acotadas, `reportedBy`, `reportedAt`, `reviewedAt`, `resolvedAt`, `ignoredUntil`, `adminState: open|reviewed|resolved|ignored`. Ninguno de estos valores cambia `availability`. Una clave estable por referencia/versión/causa y una transacción evitan incidencias abiertas duplicadas; permitir una nueva después de resolución y nueva comunicación. Se conserva el historial de observaciones mediante entradas aparte, no un array que crece sin límite.
3. `imageHistory/{entryId}` o subcolección por referencia — eventos de solo adición: registro, cambio de URL, sustitución, observación, revisión, silencio y resolución. Cada entrada contiene `actorUid`, hora, tipo, referencia e incidente; para URL anterior/nueva, guardar solo lo necesario bajo lectura administrativa y evitar copiar queries firmadas en texto de auditoría. No permitir al cliente editar o borrar entradas previas.
4. **Notificaciones internas derivadas** de incidencias abiertas o pendientes de revisión, filtradas por `ignoredUntil`. No crear una cuarta colección de avisos inicialmente: un badge y lista derivados de `imageIncidents` evitan duplicados y nuevas escrituras. Registrar `acknowledgedAt`/`reviewedAt` cuando corresponda. `src/services/notifications.js` existente crea avisos sociales en `users/{uid}/notifications` y puede enviar avisos de posts/correo; no reutilizarlo para este panel porque mezclaría avisos de usuarios con administración y multiplicaría documentos. «Imagen sustituida» se muestra como evento de historial reciente, no como alarma persistente.

La URL del post/evento sigue siendo autoridad para renderizar. Una sustitución debe actualizar el documento propietario y el registro correspondiente de forma coordinada, con idempotencia y comprobación de versión; **editar solo `imageReferences` no sustituye la imagen publicada**. No recorrer ni registrar publicaciones históricas al abrir el panel. Si falla el segundo paso de una escritura no atómica, dejar un estado de reparación observable para la nueva referencia, nunca afirmar éxito silenciosamente. Determinar durante la implementación si un lote Firestore con reglas `getAfter()` cubre ambos documentos o si conviene una operación backend autenticada; no introducir endpoint solo por comodidad.

## Permisos Firestore propuestos, no aplicados

El archivo local `security/firestore/firestore.candidate.review.rules` define `admin()`/`publisher()` con `users.role` y `isBlocked`, y termina en denegación de rutas no reconocidas. **No contiene reglas `imageReferences`, `imageIncidents` ni `imageHistory`; actualmente el candidato las deniega.** No existe evidencia en esta revisión de que ese candidato esté desplegado. El guard del router y el build privado futuro no sustituyen las reglas. Las coincidencias de Firestore se combinan mediante OR: evitar una regla amplia que abra la colección o una subcolección incidentalmente.

- **Administrador activo:** lectura de referencias/incidencias/historial. Creación y cambios de campos administrativos definidos por allowlist; al crear referencia, `availability == 'unverified'`, sin campos de comprobación técnica ni privilegios/roles. Las transiciones de incidencia se validan (abierta → revisada/ignorada/resuelta) y no permiten falsificar autor, fechas o relación. Las entradas de historial son inmutables. Si se usa Admin SDK, el endpoint verifica ID token, rol vigente y bloqueo en cada operación, valida documento propietario y campo, y aplica la misma allowlist; Admin SDK omite Firestore Rules.
- **Publisher:** **sin acceso al monitor en la primera entrega**. Sus permisos futuros requieren decidir si puede ver solo sus posts, eventos compartidos y qué incidencias puede resolver; `publisher()` global sería demasiado amplio para URLs posiblemente privadas. Su capacidad existente de editar posts/eventos no implica permiso para alterar estados técnicos o incidencias administrativas.
- **Usuario normal y visitante:** sin lectura ni escritura de estas colecciones, ni creación de incidencias administrativas. La web pública solo ve la imagen del post/evento mediante sus flujos actuales, no la URL privada del registro ni observaciones.
- **Campos de Fase B:** negar escritura desde SDK cliente de `lastCheckedAt`, HTTP, IP, redirect, SHA-256, hash perceptual, `availability` distinto de `unverified`, leases y resultados. En A tampoco existe un endpoint de comprobación. Una regla `allow write: if admin()` sin validación de campos sería insuficiente.

Las reglas de `posts` candidatas ya conceden escritura bastante amplia a admin y ciertas escrituras a publisher; `galaxyEvents` permite edición a publisher. La consistencia entre documento propietario y registro requiere validación específica. No abrir permisos globales para hacer pasar tests. Probar `list` y consultas reales por separado, además de `get`.

## Archivos mínimos y riesgos de integración

Orden propuesto: primero módulos nuevos independientes para esquema, validación y vista administrativa; después reglas candidatas y pruebas Emulator; finalmente integración puntual en guardados de `PostEditor.vue` y `EventEditorModal.vue`. `src/services/imageLibrary.js` solo debe exponer procedencia o enlace al documento, conservando su contrato actual. `src/router/index.js`/navegación administrativa se tocarían al ubicar el panel **exclusivamente** en la aplicación privada; mientras haya build único, esconder un enlace no lo hace privado. Si el panel se prueba en el build actual, todo acceso a datos debe seguir protegido por reglas/backend y no reintroducir controles de roles en web pública. Reusar `src/firebase` y `backendClient.js`; no crear otro cliente Firebase o HTTP. Mantener `resolveAssetUrl()`, `image-proxy.js`, `PostSharePage.vue` y `EventSharePage.vue` sin cambios en A.

Riesgos principales: conflictos con los cambios locales de editor/cliente HTTP; registro separado que no coincida con el post/evento; referencias duplicadas al guardar de nuevo o reordenar secciones; URL firmada expuesta en panel/log; consultas que fallen con reglas restringidas; avisos repetidos entre dispositivos; y entrada accidental del panel en el build público. La sustitución de referencia exige una operación atómica o reparación verificable. Ningún paso de Fase A debe hacer GET/HEAD de imágenes, calcular hashes remotos ni usar el proxy histórico para comprobar disponibilidad.
