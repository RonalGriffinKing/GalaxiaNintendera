## Fase 4: validación de lenguaje, rutas y cobertura

- **Sintaxis compilada: pendiente.** Se intentó Firebase Emulator Suite, pero `java` no está disponible. La revisión estática encontró 0 caracteres fuera de ASCII en el candidato y no encontró operadores mal escritos evidentes. `request.time.toMillis()`, `List.toSet()`, `List.removeAll()`, `Set.union()`/`difference()` y `Map.diff().affectedKeys()` figuran en la [referencia oficial de Timestamp](https://firebase.google.com/docs/reference/rules/rules.Timestamp_), [List](https://firebase.google.com/docs/reference/rules/rules.List.html), [Set](https://firebase.google.com/docs/reference/rules/rules.Set) y [MapDiff](https://firebase.google.com/docs/reference/rules/rules.MapDiff). Esto **no sustituye** la compilación de Rules.
- Las llamadas `get()`/`exists()` usan rutas absolutas `/databases/$(database)/documents/...` y variables de `match` (`uid`, `communityId`, `id`, `chat`) con interpolación válida. Rutas revisadas: perfil de actor, post de favorito, comunidad/membresía, usuario seguido y padre de chat. `active()` comprueba existencia antes de leer el perfil. El alta propia de `users` sigue requiriendo prueba porque `allow create` evalúa también la rama `admin()` por OR.
- La raíz `users/{uid}` no concede permisos a subcolecciones por herencia. Las subrutas declaradas son específicas. El catch-all `match /{document=**} { allow read, write: if false; }` **se solapa con todas ellas**: por OR, no revoca ningún `allow` anterior. No combinar este candidato con la regla temporal abierta ni con otro `match` amplio. Confirmación de [Firebase sobre solapamientos](https://firebase.google.com/docs/rules/rules-behavior).
- `active()` exige Auth + `users/{auth.uid}.isBlocked != true`; `admin()`/`publisher()` leen el rol de ese documento protegido por allowlist de actualización propia. El usuario normal no puede asignarse rol por `users` si estas reglas se aplican solas. Un admin sí puede asignar roles directamente; autorización y auditoría adicional siguen pendientes. La suite ahora contiene negativos de cuenta bloqueada y escritura de proyección incluso admin.
- Revisión por colección: `posts`/`sitePages` bloquean consultas públicas actuales; `users` bloquea lectura de perfiles ajenos; `communities` y `galaxyEvents` admiten consulta pública completa; `communityThreads` también, pendiente verificar privacidad de contenido; membresía permite documentos propios pero deniega contador; `directChats` permite mensaje/lectura propia pero deniega resumen de envío; `overlays` permite get exacto sin auth y solo admin dueño lista/escribe; `profileIcons`/`siteConfig` deniegan escritura cliente y dependen de Admin SDK. Estos son contratos **propuestos, no flujos funcionales demostrados**.
- El script de pruebas fija proyecto `demo-galaxia-security`, host `127.0.0.1:8055` y ahora aborta si `GCLOUD_PROJECT` apunta a otro proyecto. `initializeTestEnvironment` usa esos valores explícitos y fixtures con `withSecurityRulesDisabled` dentro del emulador. El comando de Firebase CLI se ejecutó con `--project demo-galaxia-security`; no se usan credenciales ni endpoint de producción. Seguridad absoluta frente a un proxy local malicioso no puede probarse desde el script.
- **Pruebas añadidas en Fase 4:** cuenta bloqueada frente a rutas de admin; post legacy con `scheduledAt` y sin `releaseAt` (get exacto frente a list); consulta guest de users denegada; escritura admin de proyección denegada. Sin ejecución por falta de Java. `node --check` pasó.
- **Cobertura aún faltante:** proyección pública con todos los campos/consentimiento y backfill; queries reales con índices/orden y release futuro/legacy; join/leave completo y contador atómico; chats Hub y Bubble con GIF, summary/read/hide/pin y notificaciones; overlay con documento real de todos los widgets y cambios en vivo; Storage Rules compiladas y pruebas de uploads/lecturas; fallos de `get()` por documento inexistente, cuentas bloqueadas y evaluación de límites de llamadas. La suite actual incluye tests unitarios de permisos, no una prueba de punta a punta de UI.

## Cambios del candidato

- `publicProfiles/{uid}` sigue legible públicamente, pero la escritura cliente ahora se deniega por completo. La proyección todavía no tiene sincronizador ni allowlist de campos: permitir al admin escribir cualquier mapa podía copiar correo/datos privados accidentalmente. El primer backfill necesitará una operación controlada con campos explícitos.
- `profileIcons/{id}` y `siteConfig/profileAchievements` ya no admiten escrituras del SDK cliente, ni siquiera admin. Las operaciones existentes `profile-progress.js` y `lib/progress-service.js` verifican ID token y rol admin y usan Admin SDK. La prueba se actualizó para exigir denegación cliente; el backend conserva la gestión. Esta decisión evita dos caminos de escritura con validaciones distintas.
- No se relajaron `posts`, chats, comunidades ni overlays. Sus bloqueos de compatibilidad son reales y se listan abajo.

## 1. Perfiles públicos

`ProfilePage.vue:435` lee `users/{uid}` de cualquier perfil, `:460` lista hasta 120 usuarios y `:503` completa usuarios por ID para relaciones. `PublicNavbar.vue:338`, `DirectChatBubble.vue:97` y `GalaxiaHub.vue:486` listan usuarios. El candidato protege `users` (`get` solo propio/admin, `list` solo admin), por tanto perfiles ajenos, búsqueda de usuarios, relaciones, chats y navbar pierden datos. `publicProfiles` existe solo como regla/fixture, sin sincronización real. No se puede afirmar que ya funcione.

Transición mínima: inventariar campos **efectivamente mostrados** en ProfilePage/Header/Avatar/Gamer/relaciones; crear una proyección por UID con allowlist explícita (nombre, imagen/icono, biografía, enlaces sociales consentidos, stats/recompensas públicos, roles visibles si necesarios, contadores y estados de presencia consentidos). Nunca incluir email, bloqueo, permisos, datos de auth, preferencias privadas, progreso interno o vínculos ocultos. Crear backfill validado sobre documentos existentes y actualización futura de proyección al editar campos públicos; la opción más sencilla puede ser un pequeño endpoint servidor para escrituras de perfil que actualice documento y proyección juntos. Mantener el documento original y cambiar lectores públicos gradualmente. Probar paridad de vista antes de restringir `users` en producción. `publicProfiles` solo lectura hasta concluir diseño y backfill.

## 2. Publicaciones y consultas

`PostEditor.vue:1567-1569` escribe `releaseAt` como **número epoch en ms**, 0 si `publishNow`; al cargar editor usa `releaseAt || scheduledAt` (`:1081`), lo que indica compatibilidad con un campo legacy `scheduledAt`. `Home2Page.vue:209` y `PostPage.vue:89` hacen el mismo fallback. No se verificaron datos reales de Firestore: puede haber documentos con `releaseAt` ausente o `scheduledAt` de otro tipo. La regla `publicPost` del candidato requiere valor numérico y release anterior a `request.time`; la query pública probada filtra `releaseAt <= Date.now()`. La rama fallback no puede cubrirse con esa misma query; una consulta sin filtro temporal no está garantizada por Rules.

**Decisión simple:** normalizar documentalmente todos los posts publicados a `releaseAt` numérico, 0 para inmediata, preservando `scheduledAt` legacy solo como dato histórico. Previa lectura/backup de docs reales; no hacer backfill ciego. Consultas guest de Home, búsqueda, lector relacionados, navbar y Category deben incluir `status == approved`, `visibility == public`, `releaseAt <= now` y `orderBy`/índices compatibles. Posts `unlisted` necesitan `get` por ID pero no aparecer en listas. `CategoryPage.vue:203` solo ordena por createdAt; `imageLibrary.js:29` también. `ProfilePage.vue:82,459` filtra autor sin estado/visibilidad. La consulta editor/admin puede seguir sin filtros si actor publisher/admin y la regla lo permite, pero publisher de autor propio requiere query de autoría. Fila exacta de consultas públicas en doc 14; ninguna se modificó todavía.

## 3. Comunidades y eventos

`CommunityPanel.vue:1058-1086` join/leave escribe en `users/{uid}/communities/{communityId}`, `communities/{id}/members/{uid}` y `communities/{id}.membersCount` mediante `Promise.all`; el último incremento no se permite al usuario en candidato. Si falla la tercera escritura, las otras pueden haber ocurrido: estado parcial. La prueba añadida muestra permiso esperado de los dos documentos y denegación del contador. **Opción más simple:** dejar ambos documentos de membresía con Rules por UID y calcular count desde miembros o mover solo el contador a servidor; para atomicidad real, usar batch con Rules/getAfter y comprobar invariantes, pero aumenta complejidad. No permitir increment arbitrario por usuario. Borrado de comunidad enumera miembros, espejos e hilos (`:1019-1028`) y necesita admin, límites/batches y prueba con >450 docs.

Lecturas públicas reales: `CommunitiesPage.vue:37` consulta colección; `CommunityPanel.vue:1612` escucha todas ordenadas por createdAt. Threads `:1587` ordenados por updatedAt; `Home2Page.vue` lee todos. Eventos `useEventFeed.js:15` y `CommunityPanel.vue:1639` escuchan todos con orden por startsAt; `Home2Page.vue` lee todos; `EventsPage.vue` usa feed. El candidato permite lectura total de `communities`, `communityThreads`, `galaxyEvents`: **compatibilidad de consultas**, pero también expone borradores/privados si existen. No se confirmó que esos documentos tengan status/visibility ni si contienen información privada; auditar muestras antes de mantener regla abierta. `notifyBy` de eventos permite toggle del UID propio en candidato, con prueba existente.

## 4. Chats

Dos clientes: `GalaxiaHub.vue` y `DirectChatBubble.vue`. Ambos crean mensaje en `directChats/{id}/messages`, luego actualizan resumen del padre con `lastMessage*`, `updatedAt`, `lastReadBy`, y en el Hub `deletedFor` de ambos participantes (`GalaxiaHub.vue:366-387`; `DirectChatBubble.vue:203-240`). El candidato permite crear mensaje propio y leer solo participantes, pero deniega campos de resumen y cambios de `deletedFor` ajeno: el mensaje puede existir sin actualizar inbox. La suite nueva reproduce esa denegación y permite ocultar solo con mapa propio. Lectura y marcado como leído se hacen con `readBy/seenAt` y `lastReadBy` propios; pin/clear/hide quedan acotados a UID por `ownMapChange`. `users/{uid}/notifications` permite al destinatario marcar `read` y al admin crear. `services/notifications.js` consulta todos los `users` y crea avisos a terceros: con candidato falla para no admin. No abrir escritura de notificaciones a todo usuario.

Corrección mínima futura: envío como batch de mensaje + resumen con regla que verifique (`getAfter`) que `lastMessageId` identifica un mensaje nuevo del emisor y texto/preview coincide, y que el sender solo cambió su `deletedFor`; alternativamente una sola pequeña función de envío servidor si la regla resulta demasiado compleja. Mantener cliente para read/hide/pin. Probar ambas UIs, inbox query `participants array-contains UID`, GIF, mensaje duplicado, participante ajeno, marcar leído, ocultar y notificación.

## 5. OBS

`OverlayEditorPage.vue:277-284` guarda documento completo: `widgets[]`, `name`, `format`, `width`, `height`, `updatedAt`. `OverlayPanel.vue:273-285` crea/lista/renombra/borra; el `ChatWidget.vue` guarda canal Twitch, usuario TikTok, apariencia; otros widgets guardan timer, metas, now-playing y geometría. No se hallaron credenciales en estructura de widget, pero URLs/handles, nombres y configuraciones son públicos bajo `allow get: if true`. `OverlayViewPage.vue:39` necesita `get`/listener de un documento exacto sin auth para Browser Source OBS. El candidato deniega `list` guest y escritura ajena; mantiene compatibilidad actual pero **cualquier persona con UID e ID puede leer**, y esos IDs no son secreto robusto. Antes de producción, revisar documentos reales en busca de secretos/datos personales y decidir si aceptar lectura por ID o añadir un token de enlace revocable. No exigir login a OBS sin prueba de Browser Source. La suite añadió get/list/write reales.

## 6. Storage y Netlify

No aparecen uploads directos de Firebase Storage desde `src`; se inicializa SDK en `firebase.js`. `lib/icon-image.js` guarda `profile-icons/<uuid>.<ext>` con Admin SDK, verifica firma PNG/JPEG/WebP/GIF y límite 512 KiB. `icon-storage.fragment.rules` permite lectura pública y deniega escritura cliente en ese prefijo; **fragmento no equivale a reglas Storage activas** y un allow amplio solapado prevalece. Exportar reglas activas y paths existentes. No proponer regla global de Storage hasta tenerlos.

Única función Netlify que usa `firebase-admin` según búsqueda de imports: `profile-progress.js`. Verifica Bearer Firebase ID token con revocación; el servicio revisa rol admin y bloqueo para `upload-icon-image`, `save-achievements`, create/update/delete icon. Las acciones de usuario `sync/equip/begin-read/award-read` derivan UID del token. Admin SDK omite Rules, así que esas validaciones son indispensables. `seo-files.js` y `xbox-profile.js` usan HTTP/REST; revisar IAM/token y límites por separado, pero no clasificarlas como Admin SDK. No se ejecutaron requests de producción.
